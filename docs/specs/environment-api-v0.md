# Environment API v0

Status: proposal  
Version: v0  
Owner repo: `tep-sim`  
Depends on: vendored `TEPSimulator`

## Goal

Expose TEP as a reproducible programmatic environment that can be used by scripts, deterministic controllers, agent-tool adapters, and evaluators without direct access to upstream simulator internals.

## Public lifecycle

A conforming environment MUST support this conceptual lifecycle:

```text
construct -> reset -> observe/step -> snapshot? -> intervene? -> rollout? -> close
```

The initial Python API MAY differ in names, but semantics must remain explicit and testable.

## Required contracts

### `EnvironmentConfig`

Required fields:

```text
seed: int
backend: str
control_mode: enum
record_interval: float|int
upstream_revision: str
```

Optional fields may include numerical tolerances and persistence configuration.

### `Observation`

Required fields:

```text
simulation_time
measurements: mapping[canonical_id, value]
manipulated_variables: mapping[canonical_id, value]
active_disturbances
shutdown_state
safety_margins
```

`Observation` MUST be immutable from the caller's perspective.

### `Intervention`

Interventions MUST be typed. Initial supported forms:

```text
DisturbanceIntervention(target, value)
MVIntervention(target, value)
MVConstraint(target, min_value?, max_value?)
```

Raw arbitrary writes into simulator arrays are not part of the public API.

### `StepResult`

Contains the resulting observation plus any environment events generated by the step.

### `RolloutResult`

MUST reference dense telemetry through artifacts rather than embedding arbitrarily large arrays in metadata objects.

## Required operations

Conceptually:

```python
env = TEPEnvironment(config)
obs = env.reset()
obs = env.observe()
result = env.step()
env.apply(intervention)
rollout = env.rollout(horizon=...)
capabilities = env.capabilities()
```

Snapshot/fork/replay behavior is specified separately.

## Validation order

For an intervention, the environment MUST deterministically validate:

1. schema/type;
2. canonical target identity;
3. environment capability;
4. static numerical bounds when known;
5. control-mode compatibility;
6. intervention-specific preconditions.

Failure MUST return/raise an explicit typed error before mutating simulator state.

## Control-mode rule

The API MUST make control mode explicit. Because the upstream closed-loop PI controller can overwrite manual MV changes, code MUST NOT silently accept a manual MV intervention in a mode where its intended semantics cannot be honored.

## Error classes

At minimum distinguish:

```text
InvalidIntervention
UnknownVariable
UnsupportedCapability
IncompatibleControlMode
InvalidEnvironmentState
SimulationFailure
SnapshotFailure
```

Exact class names may change; callers must be able to distinguish invalid request, unsupported request, and runtime failure.

## Provenance

Each run MUST record:

- environment version/commit;
- upstream simulator revision;
- seed;
- config;
- intervention schedule;
- run/branch identity;
- termination reason;
- artifact references/checksums.

## Invariants

- No LLM/model call occurs inside the environment.
- Same accepted config/seed/intervention schedule SHOULD reproduce results within documented tolerance.
- Failed intervention validation MUST leave state unchanged.
- Public callers MUST NOT need to import upstream internal modules to perform supported operations.

## Acceptance tests

1. Reset with identical seed/config twice and compare baseline trajectories.
2. Apply one supported IDV intervention and reproduce it.
3. Reject an unknown XMV without state change.
4. Detect incompatible MV/control-mode behavior explicitly.
5. Run a fixed horizon and persist complete provenance.
6. Execute the same test without importing any agent/runtime package.

## Non-goals

This spec does not define process topology queries, agent tools, RCA, HAZOP reasoning, recovery policy, or UI behavior.
